# Feature Specification: FK 关系条件过滤（Loader 关联加载识别原生 join 声明中的额外条件）

**Feature Branch**: `025-fk-loader-conditions`

**Created**: 2026-09-30

**Status**: Draft

**Input**: User description: "对于现在通过 FK 来做 Loader 生成的机制，想支持 FK 加上额外的约束条件（比方说 Status 等于 Active）来增强 Loader 的关联能力。软删除之类的逻辑会用到。声明方式尽量走 relationship 相关的原生描述（比方说 primaryjoin 之类），不要有额外自己定制的参数——普通 join 查询里的 and_() 模式就是同一场景，follow 那个模式是最理想的。"

## Clarifications

### Session 2026-09-30

- Q: `or_` 组合条件（如 `or_(status=='active', pinned==True)`）如何处理？平铺提取会把 OR 分支拆散成 AND，静默改变声明语义 → A: 按表达式树提取——`and_` 顶层逐项拆分，`or_` / `not_` 等布尔组合作为**整体**保留为单一条件，尊重用户声明的任何布尔组合语义（组合整体引用的列仍须在目标实体上）。
- Q: 条件在哪些消费路径生效？ → A: 全部路径——关联加载器是共享底座，条件一处声明、全部消费路径生效（entity GraphQL 嵌套、compose DTO 拼装、MCP、联邦 member 侧内嵌套）；联邦场景条件在 member 侧加载时生效，对外 wire 契约不变（条件是成员内部查询语义）。
- Q: 多对多关联表（link 表）自身列的条件（如"关联记录本身有效"）本期是否支持？ → A: 一并支持——与目标实体列条件同规则（引用列须在目标实体或关联表上），消除"一对多能滤、多对多滤一半"的能力不对称。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 列表关系的软删除过滤 (Priority: P1)

作为后端开发者，我的实体间存在大量"逻辑上只该看到一部分"的一对多关系：软删除的评论、已归档的订单明细、被驳回的审批记录。今天 nexusx 按 FK 生成的关联加载会把它们全部返回，我只能另建手写 loader 绕开自动机制。我希望在 relationship 上用 SQLAlchemy 原生的 join 条件声明（与手写 join 查询时 `and_(FK 相等, status=='active')` 完全同构的写法）声明这个约束，之后 GraphQL 嵌套字段、ER 关系解析等所有走该关系的加载路径都自动只返回满足条件的记录——不需要为过滤关系写任何加载代码。

**Why this priority**: 软删除/状态过滤是 FK 关联的最高频业务约束；当前唯一的绕行方案（`__relationships__` 手写 loader）要求放弃全部 FK 自动化（手写批量 SQL、手写列裁剪协同），代价与收益完全不成比例。这一个 story 交付后即构成 MVP。

**Independent Test**: 对一个"用户-评论"实体对（评论含 status 列，数据混有 active 与 deleted），在用户侧声明带条件的 `active_comments` 关系与不带条件的 `comments` 关系；通过关联加载查询两者，验证前者只返回 active 评论、后者行为与现状完全一致。仅交付本 story 即可交付完整价值——最常见的软删除场景闭环。

**Acceptance Scenarios**:

1. **Given** 用户实体声明了 `active_comments` 关系（join 条件含 `评论.status == 'active'`），数据中同一用户有 2 条 active、1 条 deleted 评论，**When** 通过该关系做关联加载（GraphQL 嵌套字段 / Resolver），**Then** 只返回 2 条 active 评论。
2. **Given** 同一对实体上并存无条件关系 `comments`，**When** 通过它加载，**Then** 仍返回全部 3 条（两个关系各自独立，条件不互相传染）。
3. **Given** join 条件中声明了多个额外条件（如 `status == 'active'` 且 `archived_at` 为空），**When** 加载，**Then** 所有条件全部生效（AND 语义）。
4. **Given** 带条件的关系声明为只读视图形式（SQLAlchemy 的 viewonly），**When** 应用启动与加载，**Then** 行为与未声明 viewonly 时一致（读路径不受影响；viewonly 是写入侧语义，不作为本特性的要求）。

### User Story 2 - 标量关系（多对一方向）的条件过滤 (Priority: P2)

作为后端开发者，我的外键指向的目标实体本身也可能"逻辑不可见"：审批人账号被停用、FK 指向的用户已被注销。我在多对一关系上声明同样的 join 条件后，当目标实体不满足条件时，关联加载应返回空值（None）而不是返回不该出现的实体——这与"软删除的目标实体视为不存在"的业务直觉一致。

**Why this priority**: 多对一是 FK 关联的另一半方向；软删除场景常常两侧都需要（列表侧滤掉删帖、标量侧滤掉注销用户）。实现上与 P1 同构，独立交付价值是"FK 指向的目标实体不可见时返回 None"。

**Independent Test**: 评论实体有两个指向用户表的外键（owner 无条件、approver 带"用户未停用"条件），数据中 approver 一条有效一条停用；加载两个关系，验证 approver 对停用用户返回 None、owner 不受影响。

**Acceptance Scenarios**:

1. **Given** 评论的 `approver` 关系声明了"用户未停用"条件，某条评论的 approver 指向停用用户，**When** 加载该评论的 approver 字段，**Then** 返回 None（不抛错、不返回停用用户）。
2. **Given** 同一实体上无条件的 `owner` 关系指向同一批用户，**When** 加载，**Then** 停用用户照常返回（方向间正交）。
3. **Given** 反向一对一（父侧标量形式）关系声明了条件，**When** 加载，**Then** 过滤语义与列表形式一致（条件命中则返回 None）。

---

### User Story 3 - 分页与多对多关系的同语义过滤 (Priority: P3)

作为后端开发者，当带条件的关系同时启用了关联分页（分页窗口、总计数、是否还有下一页），或关系是经由关联表的多对多时，过滤语义必须与普通列表关系完全一致：分页窗口按过滤后的集合计算、总计数是过滤后的数量（而不是全量数再被窗口过滤）、多对多的条件作用于目标实体侧与关联表侧（关联有效性）。

**Why this priority**: 分页与多对多是关联加载的两个既有高级形态；若条件过滤在这两处缺失或计数口径不一致（比如 total_count 按全量算），带条件的关系就不敢用于任何需要准确总数的界面（翻页器、进度条），特性等于只交付了一半。

**Independent Test**: 对带条件的一对多关系启用分页（limit=1），验证返回的 items、total_count、has_more 全部按过滤后集合计算；对多对多关系在目标侧声明条件，验证只返回满足条件的目标实体、对照无条件关系不受影响。

**Acceptance Scenarios**:

1. **Given** 带条件关系（过滤后剩 2 条）启用分页 limit=1 取第一页，**When** 加载，**Then** items 为过滤后按序的第 1 条、total_count 为 2、has_more 为 true。
2. **Given** 分页 offset 超过过滤后的总数，**When** 加载，**Then** 返回空页且 total_count 仍为过滤后的总数（空页不丢失计数）。
3. **Given** 多对多关系在目标侧 join 条件声明了"目标未删除"，关联表中挂着一个已删除目标，**When** 加载，**Then** 已删除目标不出现；**And** 同一对实体的无条件多对多关系照常返回它。
4. **Given** 多对多关联表自身有状态列且关系条件声明了"关联记录有效"（如成员被移出后关联被软删除而非物理删除），**When** 加载，**Then** 已失效的关联记录对应的目标实体不出现（关联有效性过滤与目标实体过滤可组合生效）。

---

### User Story 4 - 非法声明的诚实失败 (Priority: P4)

作为后端开发者，如果我声明的额外条件引用了关联加载查询根本读不到的列（比如一对多关系里引用了父实体的列、多对多里引用了源实体的列），我希望应用在启动阶段就收到明确的错误（指出哪个关系、哪个列、为什么不支持），而不是静默忽略条件（查出不该出现的数据）、也不是运行期才在具体查询上报 SQL 错误。

**Why this priority**: 静默忽略 = 数据正确性事故（条件形同虚设）；运行期 SQL 错误 = 难以定位。启动期校验是本项目既有风格（分页顺序声明等同类的校验都在启动期），把失败提前到声明确认的时刻。

**Independent Test**: 构造一个"条件引用非目标实体列"的关系并注册实体管理器，验证启动期抛出包含关系名与列名的明确错误；对照：合法声明与纯 FK 声明（无条件）均正常启动。

**Acceptance Scenarios**:

1. **Given** 一对多关系的条件引用了父实体（源侧）的列，**When** 应用启动注册实体，**Then** 启动失败，错误信息含关系名、被引用的列、以及"条件只能引用目标实体的列"的说明。
2. **Given** join 条件里出现 FK 等值对之外的双列比较（两张表各出一列但不是该关系的 FK 对），**When** 启动，**Then** 启动失败并说明仅支持 FK 等值对加目标实体列条件。
3. **Given** 纯 FK 关系（无额外条件）与合法条件关系，**When** 启动，**Then** 均正常（存量行为零变化，见 FR-005）。

### Edge Cases

- 多对一方向条件把目标滤掉 → 返回 None（不是报错，不是返回原始 FK 值）；一对多方向某父实体过滤后集合为空 → 返回空列表（不是 None）。
- 条件把某父实体的集合**全部**滤掉时，分页路径的总数兜底仍需给出该父实体的计数（0），不能因为该父实体在窗口查询中无行就丢失 total_count 键。
- 关联表（多对多的 link 表）自身列参与条件（如"关联记录本身有效"）→ 受支持：与目标实体列条件同规则（引用列须在目标实体或关联表上），作用语义为"关联有效性"过滤，可与目标实体条件组合。
- 声明带条件关系时同表存在多个外键（歧义）→ 沿用 SQLAlchemy 原生的外键指定要求（这是原生机制本来的要求，非本特性新增）。
- 条件中的比较运算符限定为 SQLAlchemy 列与常量的标准比较（等于/不等/IN、IS NULL/IS NOT NULL 等）；`or_` / `not_` 组合按声明语义整体生效（不拆散成 AND）；函数表达式、子查询参与条件 → 同"不支持形态"，启动期报错。
- 空值判断形式（如软删除的 `deleted_at IS NULL` 时间戳风格）与状态列形式（`status == 'active'`）同为受支持的一等条件形态；枚举值条件受 SQLAlchemy 字符串声明形式的命名空间限制，需以可调用（lambda）形式声明——此为原生约束，非本特性引入。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 从实体关系的原生 join 条件声明中识别"FK 等值对之外的额外条件"，并将其应用于该关系自动生成的关联加载查询（普通路径与分页路径，含分页的总数兜底查询）。提取 MUST 按表达式树进行：顶层 AND 逐项拆分为多个条件，`or_` / `not_` 等布尔组合保留为整体单一条件（组合语义不得被拆散改写）。
- **FR-002**: 条件过滤 MUST 覆盖全部自动生成的关联加载形态：一对多列表、多对一标量、反向一对一标量、多对多（目标实体列与关联表列条件均可）、以及它们的分页变体。
- **FR-003**: 分页语义 MUST 以过滤后的集合为基准：窗口、total_count、has_more 三者一致（total_count 不得按未过滤的全量计）。
- **FR-004**: 条件的声明词汇 MUST 完全复用 SQLAlchemy 原生 relationship 机制（join 条件声明），不引入任何 nexusx 自有的新声明参数、注解或 dunder。
- **FR-005**: 未声明额外条件的存量关系 MUST 行为零变化（加载结果、查询形态、错误行为均与现状一致）。
- **FR-006**: 不支持的条件形态（引用范围外实体列、非 FK 的双列比较、函数表达式/子查询）MUST 在应用启动注册实体时失败，错误信息 MUST 包含实体名、关系名、被引用的列，并说明支持的范围。多对多关系的条件引用列 MUST 在目标实体或关联表上（超出即启动期报错）。
- **FR-007**: 系统 MUST NOT 强制要求带条件的关系声明为只读视图（viewonly）；声明与否对加载行为无影响（文档可建议声明以表达写入侧语义）。
- **FR-008**: GraphQL schema 的形态（SDL、introspection）MUST NOT 因关系声明了条件而变化（条件是查询语义，不是 schema 语义；过滤后的空结果照常渲染）。
- **FR-009**: 条件 MUST 在全部消费路径一致生效——entity GraphQL 嵌套、compose DTO 拼装、MCP、联邦 member 侧内嵌套共用同一关联加载底座，一处声明处处生效；联邦场景下条件在 member 侧加载时生效、对外 wire 契约不变。

### Key Entities

- **关系条件（Relationship Condition）**: 挂在实体关系上的静态过滤约束——join 条件声明中 FK 等值对之外的部分，作用于目标实体的列；一次声明作用于该关系的全部加载路径。
- **源/目标实体（Source / Target Entity）**: 关系的两侧；一对多的源是"一"侧、目标是"多"侧，多对一相反；条件只能引用目标侧的列（加载查询只读取目标侧数据）。
- **条件关系与无条件关系并存**: 同一对实体可声明任意多个关系（条件各不相同或没有条件），彼此独立、互不影响——条件属于关系，不属于实体对。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 声明了软删除条件的关系，其关联加载 100% 不返回已删除记录（混有已删除数据的场景下零泄漏）。
- **SC-002**: 同一对实体上条件关系与无条件关系并存时，后者返回的记录集合与特性引入之前完全一致（可通过既有测试套件全量通过验证）。
- **SC-003**: 分页三要素（窗口内容、总计数、是否还有下一页）在带条件关系上全部与"先过滤后分页"的语义一致，无混合口径。
- **SC-004**: 存量应用升级到本特性后无需任何改动即可保持原有行为（全量回归测试通过，无新增告警/错误）。
- **SC-005**: 所有不支持的条件形态在应用启动阶段即失败（而非运行期或静默），错误信息足以定位到具体关系与列。

## Assumptions

- 行为基线为 SQLAlchemy 2.0 系列：join 条件带"列与常量比较"的额外条件可正常声明与配置，只读视图（viewonly）声明可选、且与关系双向声明（back_populates）兼容——以上均已在可行性验证中确认（2026-09-30，7 场景全通过、全量测试零回归）。
- 复合外键（多列 FK）维持现状不支持（既有约束，不因本特性改变）。
- 条件为静态声明：条件值在声明期固定，不提供运行时参数化（运行时过滤属于查询参数体系，不在本特性范围）。
- 多对多的条件支持目标侧（目标实体列）与关联表自身列（如 link 表的状态列，表达"关联有效性"）；引用源实体列不支持（加载查询不读取源侧）。
- 本特性不改变既有手写 loader（`__relationships__`）机制；两者并存，手写优先级照旧。
- 文档与可视化（ER 图、关系描述）不因条件变化——条件影响的是加载行为，不是关系拓扑。
